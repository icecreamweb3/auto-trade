# P5 时序数据容量优化

日期：2026-10-10

## 目标

在不降低采集粒度、不删除规范化历史行情的前提下，降低PostgreSQL长期容量增速，并保留最近3个月历史回补和最近24小时实时缺口修复所需的可写窗口。

## 已实施的第一阶段

- `raw_events`、`klines`、`ticker_minutes`、`funding_observations`、`open_interest_observations`未来新分块改为1天。
- 五张高频表启用TimescaleDB Hypercore/Columnstore。
- Columnstore排序包含主键和唯一索引字段，确保冷分块转换后仍可执行唯一性检查。
- 完整分块超过72小时后由后台策略自动转入Columnstore。
- 72小时冷却窗口长于最近24小时实时缺口检测窗口；3个月历史回补按24小时分段扫描与回补，不会反复全量扫描历史区间。
- 监控页面显示策略状态、已转换分块数和实际空间节省比例。
- 当前阶段没有配置任何retention policy，不会自动删除数据。

现有7天分块不会被重切；`set_chunk_time_interval`仅影响后续新分块。因此首次自动转换需要等待现有分块关闭并满足72小时条件。

## 与策略训练历史回补的边界

“最近3个月历史回补”是常规扫描与修复窗口，不代表任意更早区间已经存在，也不承诺日常任务会自动扫描三个月之前的数据。按 2026-10-28 计算，该窗口约从 2026-07-28 开始；`STRATEGY_SELF_TRAINING_ENGINE.md` 的正式 Cross-fit 若要从 2026-08-01 开始产生预测，在 10 天因子预热、24 小时 purge 和 30 个有效自然日训练门槛下，原始行情最迟约需从 2026-06-21 开始，因此不在本方案的常规回补承诺内。

该需求可以作为一次性、显式批准的历史回补实施，但必须在阶段 D 前另行完成：

- 先冻结 UTC 起止、Ticker/周期/数据类型清单和容量预算，按 24 小时小批次回补，受连接数、超时、CPU、临时盘和采集 SLO 限制。
- 从冻结的因子注册表展开全部训练依赖，对 Trade/Mark 1m/5m、EMA、OI、D-1 UTC 日榜/Ticker 池以及成交量、振幅、资金费等已启用输入分别验收可回补区间、覆盖率、缺口、重复、修订水位、规范化分片指纹和根指纹；仅有 K 线或任务成功状态不算完成。外部数据源的历史保留能力须实施时单独核实，不能预设历史 OI 一定可回补。
- 明确旧 Columnstore 分块的写入/重压缩方案并做容量与查询压测；不得为方便回补启用 retention 或删除既有规范化行情。
- 回补完成后由训练编排器重新生成 Cross-fit 资格报告。历史仍不足或样本门槛未通过时，不得开展正式模型 B 训练，只能继续工程原型。

因此，P5 当前实现不阻止经治理的一次性更早回补，但它本身也不证明 2026-06-21 至 2026-07-27 的数据可用；该区间必须单独取得数据源、执行并验收。

## 部署

```bash
make db-migrate
make db-storage-verify
make monitor-up
```

可在可删除的容量压测表上转换一个分块，取得本机真实压缩率：

```bash
make db-columnstore-poc
```

验证结果中五张表应满足：

- `chunk_interval` 为 `1 day`；
- `columnstore_enabled` 为 `true`；
- 每张表存在一个已调度的 `policy_compression`；
- `columnstore_after` 为72小时对应值。

## 暂未启用的第二阶段

原始事件归档和删除必须按以下顺序实施：

1. 按UTC日期导出 `market.raw_events` 到Parquet + ZSTD；
2. 为归档生成行数、时间范围、对象大小和SHA-256清单；
3. 在隔离数据库完成抽样恢复和回放验证；
4. 归档连续稳定运行后，才允许为数据库配置7天或30天retention。

在归档闭环完成以前，不得为 `market.raw_events` 添加自动删除策略。
